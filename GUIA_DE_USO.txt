QUE HAY EN EL PROYECTO
------------------------------------------------------------------------
  motor/      Motor ML: carga NSL-KDD, preprocesado (one-hot +
              estandarizacion), Random Forest con dos cabezas (binaria y
              cinco clases), Isolation Forest de apoyo, umbral calibrado
              sobre holdout interno, evaluacion sobre KDDTest+.
  api/        API REST FastAPI: /health, /predict, /predict/batch,
              /history, /metrics y /alertas. Historial en PostgreSQL
              (Neon) o SQLite en local.
  tablero/    Panel Streamlit de cinco vistas: Resumen, Analizar,
              Historial, Modelo y metricas, Ayuda. No carga modelos:
              solo consume la API.
  alertas/    Bot de Telegram con agrupacion por ventana de 10 s y
              confirmacion real de entrega (ok:true). Falta el token.
  cli/        Operacion por linea de comandos (train, evaluate, predict,
              serve, estado, alerta-prueba).
  datasets/   NSL-KDD crudo (no versionado) y muestras de prueba.
  scripts/    Descarga del dataset, empaquetado de artefactos, humo
              contra produccion.
  tests/      123 pruebas automatizadas, 84 % de cobertura.
  docs/       Arquitectura, informe de metricas, solicitud de cambio.


REQUISITOS
------------------------------------------------------------------------
  Windows + PowerShell, Python 3.12, ~700 MB libres de disco.
  Todo es gratuito y de codigo abierto (presupuesto del proyecto: $0).


ARRANQUE PASO A PASO (una sola vez: pasos 1 al 3)
------------------------------------------------------------------------
  git clone https://github.com/anorak1212/red-centinela.git
  cd red-centinela
  python -m venv .venv
  .\.venv\Scripts\Activate.ps1
  pip install -r requirements.txt
  pip install -r requirements-dev.txt

  1. Dataset publico NSL-KDD (~26 MB):
       python scripts\download_nslkdd.py

  2. Entrenar modelos (~2 minutos) y evaluar sobre KDDTest+:
       python -m cli train
       python -m cli evaluate

  3. Verificacion automatizada:
       ruff check .
       python -m pytest -q

  NOTA (maquina DTIC1, 08/10/2026): el .venv que venia en el ZIP apunta
  a otro equipo y no arranca aqui. Se creo .venv_local con Python 3.13:
       python -m venv .venv_local
       .venv_local\Scripts\python.exe -m pip install -r requirements.txt
  Usar .venv_local\Scripts\python.exe en todos los comandos de abajo.


USO DIARIO (demos)
------------------------------------------------------------------------
  Terminal 1: API  ->  http://127.0.0.1:8000/docs
       python -m cli serve

  Terminal 2: Tablero  ->  http://localhost:8501
       streamlit run tablero/app.py

  Comprobar el sistema sin abrir el navegador:
       python -m cli estado

  Recorrido de humo completo (prediccion, lote de 150 filas, latencia):
       python scripts\smoke_prod.py --api http://127.0.0.1:8000

  Consumo: la API carga ~80 MB de modelos en memoria y tarda unos 25 s en
  arrancar. El tablero gasta aparte. Al cerrar las terminales, 0.


COMO USAR EL TABLERO (5 vistas)
------------------------------------------------------------------------
  1. RESUMEN
       Estado del servicio (integridad de artefactos, umbral, almacen),
       conteo de predicciones y ataques, grafica de probabilidad,
       composicion por clase y estado de las alertas.

  2. ANALIZAR
       Pestana "Conexion individual": elegir una fila real de KDDTest+
       por familia (normal, dos, probe, r2l, u2r), editarla en JSON si
       se quiere y predecir. La etiqueta real se muestra al lado para
       que se vea si el modelo acierta.
       Pestana "Archivo CSV": subir datasets\sample_etiquetado.csv
       (150 filas, 30 por familia) y ver deteccion y acierto por familia
       por separado. Se puede descargar el resultado.

  3. HISTORIAL
       Ultimas 50 a 500 predicciones, filtros por origen y clase,
       descarga en CSV y vista de las 41 caracteristicas de un registro.

  4. MODELO Y METRICAS
       Cifras reales de KDDTest+, desglose por familia, KDDTest-21,
       holdout interno, latencia y comparativa de modelos. Nada se
       escribe a mano: sale de motor/models/metrics.json.

  5. AYUDA
       Contrato de la API, variables de entorno y que significa cada
       cifra. Incluye lo que el sistema NO hace.

  Barra lateral: URL de la API, "Comprobar conexion" y "Despertar
  servicio" (sondea /health hasta 90 s, util con el plan gratuito).


ENDPOINTS DE LA API
------------------------------------------------------------------------
  GET  /health              Estado, integridad y umbral. ?reverificar=true
                            vuelve a hashear los 80 MB de artefactos.
  GET  /metrics             Cifras del modelo.
  POST /predict             Una fila. Body: {"features": {...41 campos...}}
  POST /predict/batch       Lote hasta 500. Body: {"items": [{"features": {...}}]}
  GET  /history?limit=200   Predicciones guardadas (1 a 500).
  GET  /history/resumen     Conteos agregados que alimentan el tablero.
  GET  /alertas/estado      Si el bot esta configurado y cuantos envios hubo.
  POST /alertas/prueba      Envia un mensaje real al chat configurado.
  La documentacion interactiva (Swagger) vive en /docs.


RESULTADOS DEL MODELO (para reportar)
------------------------------------------------------------------------
  KDDTest+ (datos nunca vistos, 22,544 filas):
    macro-F1 binario 0.7995 · exactitud 0.7998 · AUC 0.9616
    precision de ataque 0.9689 · recall de ataque 0.6698
    macro-F1 cinco clases 0.4716 · F1 ponderado 0.6894
  KDDTest-21 (solo dificiles, 11,850 filas):
    macro-F1 binario 0.5808 · cinco clases 0.3734
  Holdout de entrenamiento: 0.9992 binario. NO es prueba independiente.

  Nota honesta: el criterio del proyecto pedia macro-F1 >= 0.90 sobre
  KDDTest+. No se cumple, y no por un error de implementacion: KDDTest+
  trae familias de ataque que no existen en entrenamiento (recall de
  r2l 0.09, de u2r 0.18). La literatura reporta ~0.80 como techo. El
  cambio de criterio esta en docs/SOLICITUD_CAMBIO_PERF-003.md.

SOLUCION DE PROBLEMAS
------------------------------------------------------------------------
  "La API no responde" en el tablero:
    Arrancar la API (python -m cli serve) o pulsar "Despertar servicio"
    si es el servicio desplegado y esta dormido.

  /predict devuelve 503:
    Faltan los modelos. Ejecutar python -m cli train.

  El CSV de lote se rechaza:
    El encabezado debe traer EXACTAMENTE las 41 columnas del NSL-KDD.
    Se admiten ademas label y family como verdad, y no se envian a la API.

  El historial aparece vacio tras desplegar:
    Falta DATABASE_URL. SQLite en Render no persiste entre despliegues.

  "Artefactos NO verificados" en el resumen:
    Alguien reemplazo o borro un .joblib. Revisar motor/models/ antes de
    usar la API; el boton "Reverificar artefactos ahora" lo confirma.

  Lap lenta:
    No es el proyecto (apagado consume 0). Revisar el navegador.
